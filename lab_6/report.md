# Отчёт по лабораторной работе № 6
**Тема:** Хранение, очистка и структурирование собранных данных
**Вариант:** 2 — «Книги и авторы» (HTML-каталог + API книжного сервиса)

---

## 1. Цель работы и вариант
Целью работы является построение трёхслойного хранилища данных (`raw` → `clean` → `mart`) для материалов, собранных на предыдущих занятиях. В рамках варианта №2 требуется объединить два источника разной природы: статический HTML-каталог и REST API. В чистом слое должны быть получены две связанные таблицы: **книги** (`books`) и **авторы** (`authors`), связанные по ключу автора. Объём чистого слоя должен составлять не менее 300 записей.

## 2. Описание источников и их различий
В работе использованы два типа источников:
1. **HTML-источник (`books.toscrape.com`):** статический каталог. Содержит название книги, цену в сыром виде (например, `£51.77`), рейтинг (в виде CSS-класса `Three`), наличие и категорию. Данные требуют нормализации и приведения типов.
2. **REST API (`openlibrary.org/search.json`):** возвращает структурированный JSON. Содержит `key` (work key), `title`, `author_name`, `author_key`, `first_publish_year`, `isbn`.

**Различия:** HTML отдаёт «грязные» строки (сырые значения сохранены в `*_raw`), а API — типизированные данные. В HTML отсутствуют ISBN и авторы, а в API — цены и рейтинги. Это потребовало разработки гибкой схемы и разделения логики очистки для разных источников.

**P.S.** Так как в старых вариантах были другие данные, то собрать книги и авторов пришлось заново в файлах src/collect_api.py и src/collect_html.py

## 3. Схема трёхслойного хранилища
*   **Слой `raw/`:** Файлы формата JSON Lines, режим «только дозапись» (`append-only`). Содержат служебные поля `_source`, `_source_url`, `_collected_at`, `_parser_version`, `_status`. Для HTML сохранены сырые значения (`price_raw`, `rating_raw` и т.д.).
*   **Слой `clean/`:** Файлы `dataset.parquet` (книги), `authors.parquet` (авторы), `rejects.jsonl` (отбракованные записи) и `protocol.json` (протокол очистки).
*   **Слой `mart/`:** Аналитические представления в формате Parquet и партиционированные снапшоты по дате `dt=YYYY-MM-DD/`.
*   **Пересборка:** Реализован скрипт `rebuild.py`, который позволяет пересобрать `clean` из `raw` без обращения к сети (доказательство неизменяемости raw).
## 4. Сравнение форматов хранения
Замеры выполнены на полном чистом наборе (536 записей). Источник данных — `clean/format_benchmark.csv`, воспроизводится командой `python -m src.benchmark`. Время пересчитано из секунд в миллисекунды (×1000).

| Формат | Размер (КБ) | Время чтения (полное), мс | Время чтения 2 колонок, мс | Тип `isbn` | Тип `collected_at` | Ведущий ноль |
| :--- | ---: | ---: | ---: | :--- | :--- | :--- |
| CSV | 87.87 | 4.77 | 2.02 | `object` | `object` | **потерян** |
| JSONL | 160.55 | 2.70 | 2.57 | `object` | `object` | сохранён (string) |
| **Parquet** | **37.63** | **2.51** | **1.37** | `string` | `datetime64[ns, UTC]` | **сохранён** (string) |

**Наблюдения по фактическим замерам:**
- **Размер.** Parquet в 2.3× меньше CSV и в 4.3× меньше JSONL — за счёт колоночного сжатия и отсутствия повторяющихся ключей.
- **Полное чтение.** Parquet быстрее всех (2.51 мс). CSV оказался самым медленным (4.77 мс), несмотря на меньший размер файла, чем у JSONL: узкое место — `dtype inference` в `pandas.read_csv`. JSONL (2.70 мс) обгоняет CSV, потому что `json.loads` на каждой строке дешевле, чем парсинг CSV с выводом типов.
- **Чтение 2 колонок.** Проявляется column pruning: Parquet читает только запрошенные столбцы (1.37 мс — почти в 2× быстрее полного чтения). У CSV `usecols` даёт выигрыш (2.02 мс). У JSONL выигрыша нет (2.57 мс ≈ 2.70 мс) — формат не поддерживает доступ по столбцам.
- **Типы после обратного чтения.** Только Parquet сохраняет `datetime64[ns, UTC]` и `string`-тип для ISBN. CSV и JSONL отдают `object`.
- **Ведущий ноль в ISBN.** В CSV он теряется. В Parquet при явном `string`-типе и в JSONL — сохраняется.

**Вывод:**
- **`raw/` → JSONL** — требование семантики append-only, точное сохранение сырых значений.
- **`clean/` и `mart/` → Parquet** — минимальный размер, максимальная скорость, сохранение типов, отсутствие потери ведущего нуля, нативная поддержка партиционирования.
- **CSV** — только для обмена с внешними системами. В роли основного хранилища не годится (штраф −5 по ТЗ).

## 5. Протокол очистки
Очистка реализована в фиксированной последовательности. Перед валидацией обязательных полей выполняется промоушен служебных полей (`_source` → `source` и т.д.). По результатам прогона (файл `clean/protocol.json`) получены следующие данные:

**Общая статистика прогона:**
*   Сырых записей: **545** (`books_seen=350`, `authors_seen=195`, `decode_errors=0`)
*   В clean: **536** (`books=341`, `authors=195`)
*   В rejects: **0** (ни одна запись не отбракована по качеству)
*   Удалено как дубликаты: **9** (`6` по `book_key` + `3` near-dupes по `title+author_key`)
*   Инвариант `seen = clean + rejects + removed`: `545 = 536 + 0 + 9` ✓

| Шаг | Действие | Книги (до → после) | Авторы (до → после) | Удалено |
| :--- | :--- | ---: | ---: | ---: |
| 0 | JSON decode (raw → records) | 350 → 350 | 195 → 195 | 0 |
| 1 | Нормализация текста (NFKC/nbsp/zero-width) | 350 → 350 | 195 → 195 | 0 |
| 2 | Бизнес-ключ (`book_key` / `author_key`) | 350 → 350 | 195 → 195 | 0 |
| 3 | Типизация (`Decimal` / `Int64` / UTC) | 350 → 350 | 195 → 195 | 0 |
| 4 | Пропуски обязательных полей | 350 → 350 | 195 → 195 | 0 |
| **5** | **Дубликаты по бизнес-ключу** | **350 → 344** | **195 → 195** | **6** |
| **5.1** | **Near-dupes (`title + author_key`)** | **344 → 341** | — | **3** |
| 6 | Бизнес-правила (≥5 правил) | 341 → 341 | 195 → 195 | 0 |

**Вывод по очистке:** все удалённые записи — это дубликаты (сохранена самая свежая версия). Отбраковки (`rejects`) нет, так как исходные данные успешно прошли нормализацию, типизацию и бизнес-правила.

## 6. Контракт данных и таблица проверок
Контракт реализован на `pydantic` v2. Включает в себя `BookRecord` и `AuthorRecord`. Применяются 3 `field_validator` (нормализация строк, проверка валюты, валидация ISBN) и 1 `model_validator` (проверка согласованности источника и полей: HTML-источник обязан иметь цену, API-источник — ISBN или год).

**Демонстрация на заведомо битых записях:**

| Проверка | Результат | Сообщение об ошибке |
| :--- | :--- | :--- |
| Пустой `title` | `reject` | `min_length=1` |
| Отрицательная `price` | `reject` | `gt=0` |
| Рейтинг `9` | `reject` | `rating <= 5` |
| ISBN `"12345"` | `reject` | `ISBN must be 10 or 13 digits` |
| HTML-книга без цены | `reject` | `HTML source requires price` |
| API-книга без ISBN и года | `reject` | `API book requires isbn or publish_year` |

Невалидные записи попадают в `clean/rejects.jsonl` с указанием шага, поля и причины.

## 7. Схема БД: обоснование ключей и ограничений
Для хранения используется SQLite. Схема описана в `db/schema.sql`.
*   **Первичные ключи:** `book_key` (в `books`) и `author_key` (в `authors`). URL не используется в качестве ключа.
*   **Ограничения `NOT NULL`:** на обязательных полях (`title`, `source`, `source_url`).
*   **Ограничения `CHECK`:** диапазоны для `rating` (1-5), `price` (>0), `publish_year` (1000-2100), а также строгий перечень значений для `source`.
*   **Индексы:** созданы под фактические запросы (по `author_key`, `category`, `updated_at`).
*   **История изменений:** реализована модель **SCD Type 2** в таблице `book_history` с полями `valid_from`, `valid_to` и флагом `is_current`. Это позволяет запрашивать состояние каталога на любую дату.
*   **Служебные таблицы:** `rejects`, `load_runs` (лог запусков), `quality_metrics`.

## 8. Результаты трёх прогонов загрузки (идемпотентность)
Загрузка реализована через `INSERT ... ON CONFLICT DO UPDATE` (UPSERT). После исправления логики сравнения типов (`float` vs `Decimal`) и связывания книг с авторами, загружено **536 записей** (341 книга и 195 авторов).

*   **Прогон 1 (первичная загрузка):** `inserted=536`, `updated=0`, `unchanged=0`.
*   **Прогон 2 (идемпотентность):** `inserted=0`, `updated=0`, `unchanged=536`. Поле `updated_at` **не обновилось** ни для одной записи. Это доказывает, что пайплайн идемпотентен.
*   **Прогон 3 (с изменениями):** Искусственно изменены значения двух записей (название первой книги и рейтинг второй). Результат: `inserted=0`, `updated=2`, `unchanged=534`. В таблице `book_history` (SCD2) для этих двух книг старая версия закрыта (`valid_to` установлена, `is_current=0`), и добавлена новая актуальная версия.

**Демонстрация ограничений (БД отвергла записи):**
*   `CHECK constraint failed: rating IS NULL OR rating BETWEEN 1 AND 5` — попытка вставить книгу с рейтингом `9`.
*   `UNIQUE constraint failed: books.book_key` — попытка вставить дубликат первичного ключа.

## 10. Слой Mart и графики
Слой `mart` включает 3 аналитических представления в формате Parquet:
1. `avg_price_by_category` — средняя цена по категориям.
2. `top_rated_books` — топ-10 книг по рейтингу.
3. `books_by_decade` — количество книг по десятилетиям.

Настроено партиционирование снапшотов по дате сбора (`mart/snapshots/dt=YYYY-MM-DD/snapshot.parquet`), чтение одной партиции продемонстрировано через `pd.read_parquet(..., filters=[("dt","==","YYYY-MM-DD")])`.
Построены 2 графика: распределение цен по категориям и динамика выпуска книг по десятилетиям (сохранены в `mart/figures/`).

## 11. Код vs No-code: реализация в n8n
Для no-code части был разработан workflow в **n8n** (файл `nocode/workflow.json`). На скриншоте видно успешное выполнение пайплайна.
*   **Триггер:** `Schedule Trigger` (запуск по расписанию `0 6 * * *`).
*   **Нормализация и дедупликация:** Узел `Code` генерирует 35 сырых записей (включая дубликаты и битые данные). Следующий узел `Normalize & Deduplicate` очищает пробелы, удаляет дубликаты по ISBN. В результате из 36 записей остаётся 21 уникальная.
*   **Валидация и загрузка:** Узел `IF` разделяет поток. 18 валидных записей отправляются в узел `Upsert into Books Data Table` (операция Upsert по ключу `isbn`). 3 невалидные записи (с пустым ISBN и `price="abc"`) попадают в узел `Prepare Reject Data` и затем в `Insert into Rejects Data Table`.
*   Результат загрузки валидных записей выгружен в `nocode_result.csv` (18 строк).

**Таблица сопоставления «Код vs No-code»:**

| Этап пайплайна | Чем реализован в коде | Чем реализован в no-code | Что реализовать не удалось |
| :--- | :--- | :--- | :--- |
| Нормализация полей | `step1_text`, `step3_types` | Узел `Set` / `Code` | — |
| Дедупликация | `step5_dedup` (по бизнес-ключу) | `Remove Duplicates` / `Code` | Поиск «почти-дублей» по составному ключу |
| Разделение валидных/невалидных | `pydantic` модель и `rejects.jsonl` | Узел `IF` | Сложные валидаторы pydantic (согласованность полей) |
| Загрузка (Upsert) | `INSERT ON CONFLICT` в SQLite | Узел `Data Table` (Upsert) | — |
| Расписание | `cron` / `schedule` | `Schedule Trigger` | — |
| Метрики качества и «светофор» | `quality.py` (светофор, пороги) | ❌ Невозможно | Полноценный расчёт метрик с прерыванием пайплайна |
| История изменений (SCD2) | Таблица `book_history` + триггеры | ❌ Невозможно | Отслеживание `valid_from/valid_to` на уровне no-code |

**Ключевой вывод:** Слой контроля качества (валидация контрактов, расчёт метрик, SCD2-история) плохо переносится в no-code и требует полноценного кода.

## 12. Правовой раздел
*   **Состав данных:** Названия книг, имена авторов, цены, рейтинги, ISBN. Данные являются общедоступными.
*   **Персональные данные:** Отсутствуют. Имена авторов являются публичными сведениями и не относятся к PII (персональным данным) в контексте данной обработки.
*   **Правовое основание:** Обработка общедоступных данных в соответствии со ст. 6 ч. 1 п. 1 Федерального закона № 152-ФЗ «О персональных данных», а также ст. 6(1)(f) GDPR (законный интерес).
*   **Место и срок хранения:** Локальное хранилище (репозиторий, БД SQLite). Срок хранения — до окончания проверки работы (30 дней), затем данные удаляются.
*   **Минимизация:** Собираются только те поля, которые необходимы для выполнения аналитических запросов.
